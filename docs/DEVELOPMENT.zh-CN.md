# Coding Chest 开发与测试记录

本文保留详细设计和本地测试记录。玩家使用说明请看 [简体中文](../README.md) 或 [English](../README.en.md)。文中路径以仓库根目录为基准，历史交付信息不代表 GitHub 已发布下载。

Minecraft **1.21（1.21.0）/ Fabric / Java 21** 的游戏内模组。已完成两段主走廊的本地单机扫描、编码、预览、投影导出、创造放置及撤销验收；没有上传 GitHub。独立多人服务器和其他机器的红石接线兼容性未实测。

正式模组位于 `mod/`。根目录的 Python 网页版保留为早期原型，编码规则以模组为准。

## 安装与操作

构建产物：`mod/build/libs/codingchest-0.2.0.jar`（不要安装 `sources.jar`）。与 1.21 版 Fabric API 一起放入 `mods`；Fabric Loader 至少 0.16.0。不要用于 1.21.1 或其他版本。同一实例只启用一个本模组版本。

玩家只需安装JAR并启动游戏。模组随Fabric自动加载，自动建立项目、选区和投影目录，不需要Python、终端或启动脚本。下文的构建命令仅供开发者使用。

单机安装即可使用。多人服安装同一 JAR 后可以读取完整容器数据并进行授权放置；完整服务端扫描、放置和撤销要求创造模式及权限等级 2。没有服务端支持时，未知容器内容明确报错，不当成空容器。

- **F6** 或 `/codingchest`：打开面板。
- **F7**：开关框选模式。开启后左键选择角点1，右键选择角点2（可指向64格内已加载方块）；框选点击不会破坏、使用方块或打开容器。
- **F8**：按水道编码递增顺序采样首片；指向展示框也可采样。
- **Shift+F8**：以准星方块为样本，按命中的面读取附着物。
- **Ctrl+F8**：清空首片样本。

以上只是默认键位。可在 Minecraft「选项 → 控制 → 按键绑定 → 编码全物品」修改；面板也提供「修改快捷键」入口，界面提示显示实际绑定的键位。

推荐流程：开启框选 → 左/右键选两角 → 打开面板的「选区库」命名保存 → 可继续保存其他选区 → 逐个载入识别 → 确认编码与分组 → 校对 → 生成投影。

两角分别显示金色与粉色小框，完整选区显示青色边框，其他已保存选区以较淡边框显示。选区库独立于编码配置，按世界/服务器及维度隔离保存，支持多个选区、重命名、载入和确认删除；删除记录不会修改世界方块。项目也有可浏览列表，不需要记住文件名。

每组单独识别。在「②识别 / 编码」页可推测候选结构，也可手动采样；确认首片原点、三维步进、单片数、组号和水道顺序后，可以仅保存分组配置或立即扫描，再统一扫描全部组。步进的正负表示内→外方向；空位保留地址。显示方向使用 `none/up/down/east/west/north/south`。

F8 采样展示框时会自动记录背板坐标和附着面；后续同一水道可以混排展示框、裸方块及附着物。已有样本可点“校正展示框附着方向”重新推断，识别到的背板材质加入可编辑的背景忽略列表。水道数可以按首片样本一键设置，也可以独立于进制调整，例如 **5 水道＋十进制信号**。

“物品校对”页显示位置总数、有效物品数、读取问题、非64堆叠和重复目标统计，可以筛选读取问题、重复目标、非64堆叠及空位。可以修改一个目标位置的物品 ID 列表、排除位置、批量排除非 64 堆叠物品。一个目标位置允许多种物品。同 ID 的不同朝向、含水状态仍使用同一物品编码；同物品分配到不同目标时阻止生成。

登记多组后，可在项目页点击“扫描项目全部分组”依次读取全部区域。重新全量扫描会移出旧扫描及其人工校对，请先另存需要保留的版本；取消后不能把未扫描区域的旧数据混入新结果。生成前检查每组每个位置都已有记录，不能只读取一段后生成整图方案。校对页提供经确认的“重复物品保留首个地址”，它只排除后续重复目标，保留原始排版记录。

在“④生成 / 保存投影”页计算后，可预览线框和信号标注，设置阵列原点及旋转，自动保存投影，或确认后在空气中创造放置。放置可取消和撤销；被后续修改的双箱及其附着标牌整体跳过，报告冲突坐标。

项目保存于当前游戏目录的 `config/codingchest/projects/<项目名>.json`；原始选区保存在 `config/codingchest/selections/`。点击「生成投影（自动保存）」会完成计算并直接保存，无需再选路径或解压：

`<当前游戏目录>/schematics/codingchest/<项目名-时间-唯一编号>/encoder.litematic`

同目录还保存分享用ZIP、`mapping.csv`、`signals.csv`、`materials.csv`、`project.json`、`plan.json` 和 `orientation.json`。重复生成使用新目录，不覆盖之前的投影；「打开投影文件夹」可直接定位。旧0.1版本的 `config/codingchest/exports/` 文件保留，不会自动删除。

## 编码和排版

地址固定为 **分组 / 组内单片 / 水道**。

- 二进制：1/2/4/8 组，10/11/12 位，默认8水道，可配置1～16水道；水道位宽按实际数量向上取整。组从 0 开始、单片从 1 开始、水道从 0 开始。默认按字段独立优化，可开启跨字段。使用非连续、互不重叠位组的精确子集动态规划；最大组合位宽默认 4。
- N 进制：N=10～14，三个字段的信号均为 1～N，0 不选；实际水道数可为1～N，不必等于信号进制。不是把大于9的信号当作字符串位数拼接。
- 二进制采用双层阵列，层高差 2；同一位组的信号池保持在同一层，按信号池顺序将新的位组分配到当前较短的一层。N 进制采用单层。层位是箱子空间映射，不改变地址或输出掩码；`signals.csv` 明确记录每箱层位、列号及信号。
- 每个双箱最多 50 种编码物品，前 50 格各一件（不足用命名纸补齐）；第51格5张命名纸，末3格各一把剪刀。全部槽位占用，SS2→SS1；信号池超出50种自动拆箱。
- 槽位按游戏实际合并库存计算：原版先读取右半箱（FIRST）再读左半箱（SECOND），旋转后也保持这一顺序；不能按世界坐标顺序直接拼接两个27格箱。
- 默认朝向 X+，每层沿 X+ 延伸，双箱两半沿 Z 配对。预览、放置和投影使用同一套坐标计算。
- 每个双箱的侧面附带实物告示牌，显示箱号、信号与拆分编号；二进制标牌显示完整总码长下的M掩码和V输出值。起点另有正方向牌，旋转后按实际+X/+Z/-X/-Z标注方向。文字写入原生1.21告示牌NBT，双面可读并封蜡；材料表包含所需告示牌。
- 箱体仍为2×M（或双层），标牌占据外侧边界，因此整个投影外框比纯箱体多一圈。投影子区域位置保留负侧标牌偏移，箱体锚点与预览/创造放置一致。创造生成也包含这些标牌，撤销时把箱子及其附着标牌作为关联组件，避免移除被修改标牌的支撑箱。

手动位组输入十进制掩码，例如 10 位跨字段模式下 `992,31` 表示高5位和低5位；此时需把最大组合位宽设为至少5。手动位组必须互不重叠并覆盖全部码位。

旧参考中的 `bin_pattern.sc` 提供 top/bottom 的侦测器码型，`storagetech_aid.sc` 提供容器临界填充思路，`itemlayout.sc` 提供排版提取思路。本模组不生成红石接线或侦测器电路。自动结构识别仅提供候选，需确认；模组物品的特殊方块映射可在校对页手动修正。16 堆叠、不可堆叠、自动材料收集、随机投料不在当前生成范围内。

## 构建与测试

安装 JDK 21 后，在 `mod` 目录运行：

```powershell
.\gradlew.bat coreTest assemble
```

`coreTest` 的运行时类路径**没有 Minecraft、Fabric Loader 或 Fabric API**，测试中也会验证这一点。它覆盖编码字段边界、保留的单片0、N进制信号、独立穷举对照、非连续位组、容量分箱、重复目标、空位、状态归一、排除规则、双层／单层坐标及输入校验。

普通 `test` 另外包含 Fabric Loader JUnit 下的原生比较器和 Litematic 序列化往返测试；这些不等于游戏内实测。

### 主走廊范围与0.1.0历史验收

2026-10-19 已在玩家授权的 Toka 1.21 单机地图扫描两段主走廊的左右侧，范围为 Z=513～562 和 Z=483～433，均从中心向外编号。左右各5个位置，作为10条逻辑水道采集，共1010个地址，865个有物品、145个空位。全部276个主走廊有效展示框均在网格内；另32个展示框位于中央其他功能区，不直接套用主走廊地址，未混入本次阵列。

修复空花盆映射后无未解决读取错误。原始结果包含44条16堆叠记录，验收副本仅排除这些记录、不压缩地址。4种物品存在不同目标（烟花火箭、闪烁西瓜片、平滑砂岩、平滑红砂岩），验收副本保留最小地址并标记排除6个后续目标；原始项目另存保留，可以重新选择。

815种64堆叠物品按11级信号测试配置计算得到62个双箱：分组字段20箱、单片字段22箱、水道字段20箱，共2445份编码物品。11级是为保留101列×10水道地址而选用的生成验收配置，不表示原地图现有红石机器已改为或支持11级信号。本模组不负责原机红石接线适配。

旧16箱局部测试及首轮62箱测试均已成功撤销。首轮打开真实双箱发现两半库存顺序颠倒，已修复并补充原版 DoubleInventory、四个旋转方向和合并库存 SS2→SS1 测试；旧包已在工作区改名为 `PRE-SLOTFIX-DO-NOT-USE`，仅保留作错误回归样本，不应导入使用。

最终修复版已重新导出，独立校验62个双箱、3348个填满的槽位及2445份编码物品全部一致，并在游戏中打开真实双箱确认51格5纸、52～54格剪刀的位置正确。空中实际生成62箱成功，占用位置重复生成被拦截。临时比较器接首箱实测初始输出2；用命令移出一件编码物品，触发邻居更新后输出1（这是容量信号测试，不是矿车/红石整机时序验收）。撤销时主动改动的首箱整对受到保护：先撤销122个半箱、保留2个冲突半箱，恢复原物品后重试成功撤销剩余2个。临时底座、比较器及测试阵列均已清理。

0.1.0历史投影包：`mod/run/Toka-two-corridors-N11-815items-62chests.zip`（不含0.2.0新增告示牌）。其中的Litematic使用1.21数据版本3953。旧版模组JAR的SHA-256为 `511eb5efd8e4ff5c9ca32d1321649677b0e9840dc9b57a08981c81239bcd3573`。当时24项纯核心测试全部通过；含原生注册表、比较器、合并库存和投影的测试共32项，31项通过，1项纯环境专用断言在此运行方式下按设计跳过。

本地交付副本位于 `dist/2026-10-19/`，包含同一JAR、完整投影包、独立的 `Toka-two-corridors/encoder.litematic`、地址/信号/材料表、验收项目及未排除任何物品的原始扫描。最终工作包已再次通过独立校验。开发源码仍在 `mod/src/`，没有提交或推送到GitHub。

箱数没有16的上限。N进制分别统计分组、单片、水道的信号池，每个池独立按 `ceil(不同物品数/50)` 拆箱后求和。同一物品应在三个字段各触发一次。新增回归样本中，800种物品占用8组×10片×10水道，预期56个双箱；1000种占满10组×10片×10水道，预期60个双箱。这些是可复核的测试数据，不是玩家地图的最终统计。

附件 `storagetech_aid.sc` 的编码器分支逐个读取 `encoders` 列表文件并排列双箱；其单箱填充函数对超过54项的列表会警告并截断。本模组不继承截断行为，使用约定的50种上限自动拆箱。`mod/run/Toka-complete-two-corridors.json` 是初始扫描配置（没有物品记录）；游戏实例 projects 目录内的同名文件已另存完整原始扫描，`Toka-two-corridors-N11-test.json` 是排除不支持物品和重复目标后的验收副本。

`mod/tools/verify_export.py <导出包.zip> [旋转序号0～3]` 使用历史原型的独立NBT读取器检查地址覆盖、逐物品触发信号、双箱左右配对、原版合并槽位顺序、全部54格内容以及精确分数下的SS2→SS1。它不调用模组的编码或填充代码。`audit_scan_coverage.py` 只读比较存档备份中的展示框与扫描网格，报告未覆盖位置，不自行分配地址或改动存档。

Gradle Wrapper 固定 8.8 并设置 SHA-256 校验。使用 `file.encoding=COMPAT` 规避 Windows 中文路径的 Java 参数文件编码问题，Java 源码和资源处理仍明确使用 UTF-8。
